## 2. 环境适配（本项目的关键难点）

本机是 **Android 手机上的 Ubuntu 24.04 aarch64（glibc）容器**，而 Google 只发布
**x86_64** 的 Android 构建工具，官方 Maven 上**不存在 linux-aarch64 版的 aapt2**
（实测 8.7.3 / 8.9.3 / 8.11.1 / 8.13.0 四个版本，全部 404），
SDK 自带的 aapt2 / aapt / zipalign 也全是 x86_64 ELF。

解决方案：
1. 从 Termux 仓库取得 **aarch64 版 aapt2 16.0.0.4**；
2. 该二进制为 Android bionic 链接，补齐其依赖库
   （libc++、libprotobuf、abseil、fmt、expat、libpng、libzopfli、zlib）；
3. 用 shim 脚本 `/opt/goldlab-tools/bin/aapt2` 注入 LD_LIBRARY_PATH 后执行；
4. 通过 `android.aapt2FromMavenOverride` 交给 AGP。

其余工具：Temurin **JDK 21**（完整 JDK）、**Gradle 8.11.1**、
**Android SDK platform-35 + build-tools 35.0.0**。

下载加速：华为云 Maven 镜像实测 **4.3 MB/s**（官方源约 0.1 MB/s），
Gradle 发行包走南京大学镜像约 **1 MB/s**。

## 6. 关键规则与假设

1. **同根 K 线止损止盈冲突**：只有 M1 OHLC，无法知道盘中高低点先后。
   两者同时被触及时一律按「**先触发止损**」的保守规则处理，
   该说明写入交易记录备注字段，并在交易界面提示。
2. **报价模型**：行情为 BID；买入成交在 ASK = BID + 点差，卖出成交在 BID。
3. **时间基准**：按经纪商服务器时间解释，统一以 UTC 换算为 epoch，不做时区推断。
4. **广告奖励上限**：4000 USD 约束的是**逐条观看奖励**；
   满 20 条的 1000 USD 里程碑奖励为独立奖励，不计入该上限
   （否则 20 × 200 = 4000 会让里程碑奖励永远拿不到）。
5. **合约规格为模拟参数**，不代表任何真实经纪商；界面已明确说明。

## 10. 版本历史

### 0.1.1 — 修复「行情不会动」

**现象**：点播放后界面显示「回放中」，但价格与时间完全不动。

**根因**：ReplayEngine.play() 里协程体的存活判断错误地读取了可变的 job 字段。
viewModelScope 使用的是 Dispatchers.Main.immediate，而 immediate 调度器在
「已经在主线程」时不派发，协程体会在 launch() 返回之前就同步执行——
那一刻 job 字段还是 null，循环条件 job?.isActive == true 立即为假，循环直接退出；
界面上的 playing 标志却已被置为 true，于是表现为「显示回放中但不动」。

**修复**：
1. 用 CoroutineStart.LAZY 启动，先给 job 赋值再 start()，保证协程体运行时字段已就绪；
2. 循环内改用 coroutineContext.isActive 判断自身存活，不再读可变字段；
3. 循环退出时兜底清除 playing，杜绝「假装在播放」的状态残留。

**验证**：新增 ReplayEngineTest 共 5 个用例，使用 Dispatchers.Unconfined
（与 Main.immediate 同为「无需派发、同步执行」）稳定复现该缺陷。
把旧逻辑放回去跑，4 个用例失败，报错分别为：
应停在最后一根 expected:<4> but was:<0>、slow=0 fast=0、
play() 后 playing 应为 true、已在运行时再次 play() 不应启动新任务；
换回修复版后 5 个用例全部通过。

**同时改进**：新增启动加载界面。此前 loading 状态从未被任何界面使用，
重新载入 127MB CSV（需重新建索引约 18 秒）期间界面完全静止，观感与卡死无异。

当前测试总数：**60 个用例，0 失败**。


### 0.1.2 — 修复闪退并加入日志

**现象**：播放一段时间后闪退。

**取证**：本机无法 adb 安装调试，但可以读设备日志。直接从 logcat 拿到了真实堆栈：

    FATAL EXCEPTION: main
    Process: com.goldlab
    java.io.IOException: Bad file descriptor
        at sun.nio.ch.FileChannelImpl.position0(Native Method)
        at com.goldlab.data.csv.CandleIndex.readLine(CandleIndex.kt:74)
        at com.goldlab.data.csv.CandleIndex.barAt(CandleIndex.kt:61)
        at com.goldlab.engine.ReplayEngine.advance(ReplayEngine.kt:195)
        at com.goldlab.engine.ReplayEngine.runLoop(ReplayEngine.kt:179)

**根因**：SafUriHandle 里的 ParcelFileDescriptor 只是一个局部变量，
没有任何强引用。它被 GC 回收时 finalizer 会关闭底层文件描述符，
而我们早已把基于该 fd 的 FileChannel 返回给了调用方——
之后任何 position() / read() 都抛 Bad file descriptor。

这也解释了崩溃的时间特征：刚载入时若干次读取是好的（GC 还没跑），
播放一会儿后 GC 回收了 pfd，下一次读取立刻炸。
改用本地文件（非 SAF）不会触发，因为它不涉及 pfd。

**修复**：
1. SafUriHandle 强引用 pfd 与 FileInputStream，并新增 close() 显式释放；
2. CandleIndex.close() 一并释放 handle；
3. CandleIndex.barAt() 捕获读取异常，作废句柄重开一次，仍失败则返回 null，绝不抛给上层；
4. ReplayEngine 回放循环加 try/catch，出现异常只暂停并提示，不让应用闪退；
5. 修正换源顺序：先暂停回放再关闭旧数据源（此前可能读到已关闭的索引）。

**新增日志功能（本次要求）**：
- GoldLabLog：全局未捕获异常处理器，把完整堆栈 + 设备/版本/内存信息
  写入 crash-<时间戳>.txt，然后交回系统处理器，不吞掉崩溃；
- 运行日志 goldlab.log，超过 512KB 自动轮转；
- 日志目录（应用专属外部目录，无需任何存储权限）：
  /storage/emulated/0/Android/data/com.goldlab/files/logs/
- 新增「设置 → 日志与诊断」页面：列表、查看、分享（FileProvider）、
  导出（SAF）、刷新、清空；有崩溃记录时页面顶部高亮提示；
- 关键动作已埋点：启动、行情源载入、CSV 导入报告、下单、账户重置、回放异常。

**测试**：新增 CandleIndexResilienceTest 5 个用例（构造一个随机读必抛
IOException 的句柄，验证 barAt 返回 null 而不是抛异常，并保留正常句柄的对照组）。
当前测试总数：**65 个用例，0 失败**。

### 0.1.5 — 图表周期选择

新增图表周期：M1 / M5 / M15 / M30 / H1 / H4 / D1。

- 数据源始终是 M1；其他周期由 M1 **现场聚合**，与 MT5 一致，不补造缺失的分钟。
- 对齐规则：M1~H4 按 epoch 整数倍对齐（H4 边界为 UTC 00/04/08…），D1 对齐 UTC 自然日。
- 入口：图表页左上角符号旁的周期标签（如「M1 ▾」），点开选择。回放位置不变。
- 指标与图表同周期：M15 上的 EMA20 就是 20 根 M15（MT5 行为）。
- 回扫上限 MAX_M1_SCAN = 150000 根 M1：D1 想要 400 根需回扫 57.6 万根，
  在手机上会明显卡顿，因此截断（D1 实际约 100 根），切换时图表上有加载提示。
- 周期选择会持久化，下次启动恢复。

新增 CandleAggregatorTest 共 9 个用例，其中关键一条是
**增量合并结果必须与整段聚合完全一致** —— 回放是逐根 M1 走的，
两者不一致就会导致图表与真实数据不符。当前测试总数 **74 个用例，0 失败**。

**同时修复一个从未生效的功能（重要）**

原 CandleChart 的手势挂在 pointerInput(Unit) 上。这个 key 让手势协程只创建一次，
于是它把**首次组合那一刻的 bars 列表按值捕获**了。而图表的加载遮罩是画在图表**上面**的
（图表本身从进页面起就存在），所以首次组合时 bars 还是空列表 ——
判断 bars.size < 5 永远成立，**双指缩放与单指平移从未真正生效过**。

改用 rememberUpdatedState 在手势回调里读取最新的 bars 之后，手势才能拿到实时数据。
这是一个静默失效的缺陷：没有任何报错，只是操作没反应。

**新增可测的几何层**

把图表的数学全部抽到 ui/chart/ChartMath.kt（纯函数，不依赖 Android 框架）：
可见窗口、价格范围、像素↔价格、像素↔索引、拖动平移、锚点缩放。
UI 只负责调用与绘制，于是这些交互第一次有了回归测试。

新增 ChartMathTest 共 28 个用例，其中两条是**先失败后修复**的真缺陷：

锚点必然跟着右边界滑动 —— 这是所有图表软件的共同行为，不是缺陷。

当前测试总数 **102 个用例，0 失败**。

### 0.1.7 — 修复「阳 K 线闭合后没有实体」

**现象**：一根阳线在未完成时看得出有实体，一旦收盘（下一根出现）实体就像消失了。

**根因**：实体浓度前后不一致。原代码把两种状态分开写 ——
未完成画 color.copy(alpha = 0.28f)，而已收盘的阳线只画 color.copy(alpha = 0.18f)。
于是阳线收盘那一刻，填充浓度反而**从 0.28 掉到 0.18**；
再叠一根 1.1px 的全浓度描边，小实体就只剩一个空框 —— 正是「闭合后没有实体」。

根子在于「用填充浓度区分未完成 / 已完成」这个做法本身就是错的：
两者应该只在**边框样式**上区分，实体浓度必须一致。

**修复**
1. 阳线实体默认改为**实心**（与阴线一致，可读性优先）；
2. 未完成 K 线改用「整体 alpha 0.8 + 虚线边框」标记，实体浓度与已收盘的完全一致，
   收盘瞬间不再有任何视觉变化；
3. 保留 MT5 式空心阳线，但做成设置项「阳线空心」，且空心时内部给一层
   明确可见的淡填充（0.30），不会退化成空框；
4. 实体几何抽到 ChartMath.bodyTop / bodyHeight，并保证最小 1px ——
   十字星（开收相等）不会整根消失。

**同时修复**：「图表显示」的几个开关此前**只写不读**，改了设置重启后全部回落到默认值，
用户会以为开关没生效。已在初始化时读回。

新增 5 个实体几何测试（十字星最小高度、亚像素实体不被价差吃掉等）。
当前测试总数 **107 个用例，0 失败**。

### 0.1.8 — 指标副图

**先发现的死开关**：设置里有「显示 RSI / ATR 指标面板」这一项，
但 showRsi / showAtr **从来没有被任何渲染代码读过** —— 项目里根本没有指标面板。
RSI / ATR 只是图表左上角图例里两个恒定显示的数字，开关拨来拨去没有任何效果。

**实现**（结构参考收藏里的 ccBiver/chartkit 的 Pane 设计）

1. 主图下方新增指标副图，每个指标占一条独立窗格；
2. 副图与主图**共用同一套 ChartMath 坐标换算**，所以缩放 / 拖动天然同步 ——
   副图不持有自己的视图状态，否则两边必然错位；
3. RSI 固定 0..100 并画 30 / 70 参考线（不能随窗口浮动，否则 60 和 65 看起来天差地别）；
4. ATR 没有天然区间，按窗口自适应；
5. **跨无效值断开**：指标预热期是 NaN，必须断开而不是连到 0 ——
   这是 chartkit 的 IndicatorLine 注释里明确强调的坑，连到 0 会出现「指标掉到底部」的假象；
6. 十字光标：竖线贯穿主图 + 全部副图；横线只在光标所在的那条窗格内
   （落在 ATR 上的横线不能拿主图价格去解读）；右侧标签按窗格显示各自取值；
   副图左上角读数在光标激活时显示光标那根的值，而不是末值。

**同时修一个被测试抓到的真 bug**：seriesRange 原本用 Double.MAX_VALUE 当哨兵，
但它是 **finite** 的，于是「窗口内一根有效值都没有」这个判断永远不成立，
会返回 ±MAX_VALUE 量级的垃圾区间。已改为显式标志位。

**空间不足时宁可不画副图**：splitPaneHeights 保证主图至少 120dp，
放不下就先退到副图最小高度，仍不够则返回 paneHeight = 0。

新增 10 个测试，其中一条是不变量断言：**主图 + 全部副图的像素和必须等于可用高度**，
像素不能被「分配」吞掉。
当前测试总数 **117 个用例，0 失败**。

**注意**：RSI 与 ATR 两个开关默认都是开，所以会同时出现两条副图，
主图高度约占 66%。不需要的可以在 设置 → 图表显示 里关掉。

### 0.1.9 — 指标工具库：自选 + 调参

需求：让用户自己搭配指标、自己调参数，并且提供十几个传统指标。

**17 个传统指标**（主图叠加 6 个 / 独立副图 11 个）

| 主图叠加 | 独立副图 |
|---|---|
| SMA、EMA、WMA、BOLL 布林带、唐奇安通道、SAR 抛物线 | VOL 成交量、MACD、RSI、KDJ、ATR、DMI/ADX、CCI、W%R 威廉、MOM 动量、ROC 变动率、OBV 能量潮 |

每个指标都带参数字段与元数据（默认值、上下限、步进、是否整数），
界面据此生成「− 数值 +」控件，越界一律夹回合法范围。
同一个指标**可以添加多次**并各自调参（EMA(20) 与 EMA(50) 同时叠加是最常用的用法）。

**分层**（这一版最重要的结构决定）

    indicators/Indicators.kt        25 个纯函数（SMA/WMA/BOLL/MACD/KDJ/ADX/CCI/SAR…）
    indicators/IndicatorCatalog.kt  17 个指标的定义 + 参数元数据 + 求值 lambda
    indicators/IndicatorConfig.kt   用户配置模型 + 文本编解码 + 求值引擎

    ui/screens/IndicatorScreen.kt   管理界面

indicators 包**不依赖任何 UI 类型**，所以整套指标数学与配置逻辑都能纯 JVM 单测；
颜色、布局这些只属于显示的东西全部留在 ui.chart。

**配置持久化用文本而不是 JSON**

格式：ema:period=20|ema:period=50|macd:fast=12,slow=26,signal=9

理由是容错：这个字符串塞进 SQLite 的一个 setting，手写编解码可以做到
未知指标丢弃、非法数字忽略、缺失参数补默认，不会因为一个字符坏掉就丢掉整套配置。
另用一个哨兵值区分「用户清空了指标」与「从未配置过」——
否则用户删光指标、重启后又被默认配置填回来。

**副图规格泛化为多线**（MACD = DIF + DEA + 柱；KDJ = K + D + J）

它们量纲相同、共用一根 Y 轴，拆成多个窗格反而无法比较。
柱状线按正负自动着色，并且在算值域时**把零轴并进来**，否则柱子越长越画到窗外。

**测试抓到的真 bug**

IndicatorConfig.withAdded 不校验 defId 是否存在。原因是它依赖
IndicatorInstance.normalized()，而后者对未知 def 是「无操作」，
于是不认识的 id 被原样塞进配置 —— 界面上显示着一项，但永远算不出结果。
withReplacedAt 有同样的问题。两处都已改成显式校验。

另有两条测试是**我自己算错了**（不是代码错），一并修正：
KDJ 那条我以为一路上涨时 RSV 恒为 100，实际按 high=close+1 / low=close-1 的
构造，周期 9 的 RSV 恒为 90（(close-ln)/(hn-ln)=9/10）。
改成断言收敛到 90，反而变成了对 RSV 公式的精确校验。

**同时删除**：设置里那两个死开关（显示 EMA20/50、显示 RSI/ATR 面板）
换成「管理技术指标」入口。

新增 IndicatorCatalogTest 35 个用例（目录完整性 / 指标数学 / 配置编解码 / 配置操作）。
其中一条是目录不变量：**17 个指标每一个都必须在 300 根真实长度的数据上算出正确形状**，
不许有「注册了但算不出来」的指标。

### 0.1.10 — 历史数据持久化与回放存档

**用户报告**：历史数据每次重启都回到最开始，而不是停在回放到的位置。

**根因**：存档写进去的身份和恢复时用来比对的根本不是同一个东西。

    persistReplay:  sourceId = currentSource?.sourceName      // 给用户看的显示名
    initialLoad:    progress.sourceId == lastId               // lastId 是 file:/… 或 uri:…

显示名永远不可能等于 file:/… 这种持久化 id，于是条件恒假、startIndex 恒为 0。
更隐蔽的是：没有导入真实文件（用 DEMO）时 lastId 为空串，短路条件成立、能正常恢复 ——
所以这个 bug 只在导入了真实 CSV 之后才出现，看起来像「只有我的数据有这个毛病」。

**修复**

1. 新增 engine/ReplayResume.kt：来源键（SourceKeys）+ 恢复判定（ReplayResume.decide）。
   **显示名与身份彻底分开**：显示名给界面，身份给比对。
   判定抽成纯函数，是因为它原本埋在 initialLoad 里、一个 != 写反就静默失效
   （不报错、不崩溃，只是位置永远回到开头），恰恰最该被测试盯住。
2. 存档**按数据源分别记一份**（新表 replay_bookmarks）：整段 134MB 的 CSV 与按月拆分的文件
   各有各的位置，不再互相覆盖。
3. 修掉一个连带缺陷：onNewBar 里原本是

       if (有成交) { 存交易 } else if (够 25 根) { 存回放进度 }

   一旦这根 K 线触发了成交，回放进度那次落库就被整根跳过；成交频繁时进度几乎存不下去。
   已改为两件事彼此独立。
4. 切后台无条件落库：原来只在「正在播放」时才存，用户停着看行情再切走就丢了。
5. 落库加了脏检查：内容没变就跳过写库，回放时不再每 25 根都做一次无意义的 INSERT。
6. 载入完成时明确告诉用户恢复了没有（第 N 根 / 存档超范围已夹到末根 / 这是另一个数据源）。
   静默恢复和静默失败一样糟。

**同时修掉一个数据损坏隐患**

GoldLabDatabase.onUpgrade 原本是：

    DROP TABLE account / trades / replay_state / settings / ad_state / daily_results
    onCreate(db)

只要版本号加一，用户升级一次就会**丢光全部交易历史和设置**。这不是迁移，是数据损坏。
本次因为要加 replay_bookmarks，必须动版本号（v1 → v2），改成严格可加性迁移：
只执行 CREATE TABLE IF NOT EXISTS，老表一行不动。注释里写明了后续只允许可加性变更。

**「存档」界面**：数据管理页新增「回放存档」卡片，显示当前数据源、已回放到第几根、倍速，
并提供「从存档继续」「从头开始」「删除存档」。删除存档只影响回放位置，不动账户与交易记录。

**兼容性**：你手机上现在装的是 v1 数据库。升级到本版会执行 v1→v2 迁移，
只新建一张表，交易记录、账户余额、设置全部保留。旧的 replay_state 表保留但不再使用。

新增 ReplayResumeTest 13 个用例，含一条不变量：
**任意 (数据长度, 存档索引) 组合下返回的索引都必须落在 [0, size) 内**。
当前测试总数 **168 个用例，0 失败**。

### 0.2.0 — 挑战模式：开局负债 + 每日还款（本轮）

**背景**：此前的产品形态是「模拟器」而不是游戏 —— 没有目标、没有胜负判定、没有进度。
这在审核上也有对应条款：审核规范 1.6.9「**不具备游戏玩法与游戏属性的应用软件**」暂不收录。

**核心机制：开局就背债，每个行情日必须还一次钱**

压力从第一秒就存在，而且「买了拿着不动」这个偷懒策略被每天的现金流义务直接废掉。

三条被测试锁死的规则：

1. **还款先抵利息、再抵本金** —— 利率越高本金降得越慢，「贪心有标价」自然成立；
2. **还款本身不改变净值**（现金 -100、负债 -100 两者抵消），**只有利息真正吃掉收益**。
   所以净值增长 = 交易盈亏 - 累计利息。有一条测试专门断言这个等式；
3. **违约优先于一切** —— 即使净值已超标，只要现金不够还款就判负。

**行情日按「累计行情时间」计，不按现实时间**

回放可以加速到 10 倍。若按现实时间计息扣款，**加速就等于少付钱**，规则会自相矛盾。
所以累加相邻 K 线的时间戳差，满 24 小时行情时间算一个行情日。

也不能用「日期变化」计：黄金周日 23:00 开盘，实测约 55 根 M1，
按日期会被算成一个完整交易日，凭空多扣一次款。有一条测试专门灌 55 分钟、要求天数为 0。

**六个关卡，数字全部来自真实数据**
（2021-01 ~ 2026-09 共 70 个月逐月统计涨跌幅、月内最大回撤、振幅后挑出来的）

| 关卡 | 区间 | 真实行情特征 | 开局余额/负债 | 日还款 | 日息 | 目标 |
|---|---|---|---|---|---|---|
| 顺势 | 2024-03 | +9.8%，回撤仅 2.5% | 1000 / 500 | 25 | 0.30% | 575 |
| 现金流 | 2022-12 | 振幅仅 3.8%（窄幅横盘） | 900 / 700 | 40 | 0.40% | 300 |
| 逆势 | 2026-06 | -11.8%，单边下跌 | 2000 / 1500 | 70 | 0.60% | 620 |
| 风暴 | 2026-03 | 回撤 24.3%，区间内最凶 | 3000 / 2000 | 110 | 0.80% | 1150 |
| 贪婪 | 2026-01 | 振幅 29.7%，中途挖 16% 坑 | 1500 / 1200 | 60 | 0.60% | 420 |
| 冲刺 | 2025-09 | +12.0%，回撤仅 2.0% | 2500 / 2000 | 110 | 0.90% | 680 |

**关卡表自带校验，而且它真的抓到了错误**

ChallengeCatalog.validate() 检查：目标必须高于开局净值、现金必须够还完整个区间、参数符号等。
跑测试时它直接失败 —— storm-2026-03 的开局净值是 3000-2000=1000，而目标被写成 950，
**意味着这一关什么都不做就算通关**。已改为 1150。

**校验用「行情日估值」而不是日历天**

第一版用日历天算「现金够不够还到月底」，结果 2022-12 被误判成必死局 ——
该月 31 个日历日但只有约 22 个行情日。用日历天校验会把本来能通关的关卡误判成陷阱。

**分层**

    domain/challenge/ChallengeDef.kt      关卡定义 + 实时快照 + 结果枚举
    domain/challenge/DebtSchedule.kt       每日结算（计息、还款、提前还款）
    domain/challenge/MarketDayClock.kt     行情日时钟
    domain/challenge/ChallengeRuntime.kt   挑战运行时状态机
    domain/challenge/ChallengeJudge.kt     胜负判定 + S/A/B/C/D/F 评级
    domain/challenge/ChallengeCatalog.kt   6 个关卡配置 + 表自检
    ui/screens/ChallengeScreen.kt          关卡列表 + 进行中面板 + 结算画面

**引擎接入只改了一处关键点**

Account 增加 debt 字段，equity 从「余额 + 浮动」改为「余额 + 浮动 - 负债」。
就这一处，**现成的风控全部自动正确** —— 爆仓判定、可用保证金、强平线用的都是 equity，
不需要为负债改任何一处风控代码。

新增 ChallengeTest 33 个 + ChallengeRuntimeTest 20 个用例。
当前测试总数 **221 个用例，0 失败**。

### 0.2.1 — 关卡数据随包内置（本轮）

**问题**：挑战模式要求用户先手动导入 134MB 的 CSV 才能玩。
一个游戏不该这样，而且对 TapTap 分发来说这是致命的。

**做法**：把 6 个关卡月份的行情打进 `assets/challenges/`。
原始 12.34 MB，APK 的 zip 压缩后 3.44 MB，APK 从 10.5 MB 增至 13.46 MB。

解析**完全复用**已测过的 `CsvCandleParser`，不引入新格式 —— 
新格式就意味着新的解析风险，而我没有真机可以验证。

一个月约 3 万根 M1，全部读进内存约 2 MB，因此直接用 `InMemoryBarSource`，
不需要文件索引那一套。加载一次的耗时可忽略。

挑战**一律使用内置数据**，理由有两条：

1. 关卡的难度参数（目标净值、还款额、回撤上限）是针对这份数据调出来的。
   换成别的经纪商的 CSV，同一个月的走势可能完全不同，关卡就失效了；
2. 用户不需要做任何准备就能开局。

用户导入的数据仍然保留，用于自由练习。退出挑战时原来的数据源会原样还回去，
挑战期间也**不回写回放存档**（否则会把自由练习的进度覆盖掉）。

#### 踩到一个会让功能直接失效的坑

源文件放成 `.csv.gz` 时，**aapt2 会把它解压并按 `.csv` 存进 APK**
（Android 的 AssetManager 对 gz 资源有透明解压处理），于是按 `.csv.gz` 去找会直接找不到。
而且 APK 的 zip 本身就会 deflate，**预压缩没有任何收益**。

这个问题的性质值得记一笔：它不会编译报错、不会让测试失败，
**只有在真机上打开关卡时才发现「数据缺失」**，而我没有真机。
是靠解包检查 APK 的资源清单才发现的。

修法是不依赖文件名：`.csv` 与 `.csv.gz` 两种名字都试，
并且**按内容嗅探 gzip 魔数**（0x1f 0x8b）决定要不要解压。
这样无论 aapt2 怎么处理资源，都能正常工作。

同时把「APK 里的资源名 vs 加载器会去找的名字」做成了构建后的固定校验步骤 —— 
这次就是它抓到的。

#### 【必须确认】数据许可

**这批行情数据来自用户本机的 MT5 导出（Exness）。**
把它打进 APK 并分发到应用商店，属于**再分发经纪商的行情数据**，
是否被允许取决于该经纪商的数据条款。

### 0.4.0 — 新增玩法「猜涨跌」（本轮）

用户反馈「挑战关不太好用」，要求换一种玩法，在候选里选了「猜涨跌」。

#### 动手写代码之前，先用真实数据做了两个验证

**验证一：M1 上到底有没有可利用的方向性？**

用内置的 2024–2026 真实 M1 数据做对照实验，七种选向方式各跑约 3500 局（1 手、持有 60 分钟）：

| 选向方式 | 胜率 | 每局均值 |
|---|---|---|
| 随机（无技巧基线） | 46.8% | −19.92 |
| 跟最近 1 根 | 47.4% | −10.46 |
| 跟最近 5 根 | 48.1% | +8.51 |
| 跟最近 15 根 | 48.7% | −22.31 |
| 跟最近 60 根 | 45.0% | −62.71 |
| 反向跟最近 5 根 | 48.4% | −41.13 |
| 反向跟最近 60 根 | 48.6% | −24.51 |

结论：**全部落在 46%~49%，差异都在噪声里，M1 上没有可利用的方向性。**
（每局均值那一列围绕 −20 上下摆动，而 −20 正好就是一次往返的点差成本 = 0.20 × 100 盎司。）

这个结论直接改变了设计。原本打算做「点一下涨/跌，然后干等结果」——
那会是一个点完就发呆的硬币游戏。改成：
**入场之后逐根揭晓，什么时候平仓由玩家自己决定。**

**验证二：用真实数据校准止盈止损与点差**

- XAUUSD 的 M1 ATR(14)：不同月份在 **0.38 ~ 3.18** 之间（随年份与波动率走）
- 每根 K 线自带真实点差：**0.16 ~ 0.28**，占 ATR 的 **5% ~ 48%**
- 模拟三组预设止盈止损（{1,2,4} / {1.5,3,4.5} / {2,3,4} × ATR，各跑 6000 局）：
  **每一档的实际胜率都精确等于它自己的「打平所需胜率」**
  （例：{1,2,4} 的「快跑」胜率 71.5%，打平需 76.0%；「扛住」胜率 20.1%，打平需 20.9%）

最后这条让设计砍掉了一半：原本有三档预设出场策略（快跑 / 均衡 / 扛住），
模拟确认它们不过是**同一个期望的三种分布** —— 机器执行规则不产生技巧，只有人做决定才会。
所以砍掉预设，改成手动平仓。

#### 玩法

1. 看 60 根 M1（1 小时）历史，猜接下来 1 小时涨还是跌；
2. 猜涨 = 做多，猜跌 = 做空，按当前价**立即成交**（含真实点差，取自数据本身的点差列）；
3. 之后**逐根揭晓**，玩家随时可以点「平仓」把当前的盈亏锁定；不点就走满 60 根按市价强制平仓；
4. 结算后图表把**剩下的窗口一次性揭开** —— 让人亲眼看见「我走了之后，它去了哪里」。

#### 关键设计：让「处置效应」变成可测量的数字

战绩条上并排四个数字，其中一个是本项目独有的：

| 指标 | 含义 |
|---|---|
| 胜率 | 与「抛硬币 50%」并排显示，随时知道自己在不在瞎猜 |
| 盈亏比 | 平均盈利幅度 ÷ 平均亏损幅度 |
| **持有比** | **亏损时平均持有根数 ÷ 盈利时平均持有根数** |
| 打平所需胜率 | 在当前盈亏比下，要不亏需要多高的胜率 |

「持有比」是玩家自己造成的、最容易忽略、也最扎心的一项。
≥ 1.5 时界面直接给出那句话：

> 赢的时候平均拿 4.0 根，亏的时候拿 22.0 根 —— 亏损时拿得久 5.5 倍。

结算卡还会给出**复盘对照**：如果入场时就挂一个 1.5×ATR 的固定止损，
会挂在哪、第几根被打掉、只亏多少。这是为了回答那个最扎心的问题：
「你本来可以只亏这么多。」

#### 测试

新增 **GuessGameTest 35 个用例**，分三层：

1. **规则层** —— 成交价、方向、点差成本、结算、复盘对照，逐条钉死。
   其中一条：价格**完全不动**时，猜涨猜跌都必亏 20 美元（两个方向各付一次点差）。
2. **出题层** —— 随机窗口前后都留够、答案不与题面重叠、同种子可复现、
   数据缺列时点差退回保守默认值（绝不能当成 0，那等于白送一次免费交易）。
3. **行为层**（这个玩法存在的理由）—— 用随机游走模拟一个「赚 5 美元就跑、亏了扛到底」的玩家，
   跑 400 局，断言它**必然**产出「持有比 > 1.5、盈亏比 < 1」；
   另一条对照组断言：随机方向 + 走满时间的胜率必须贴着 50%，且每局均值为负（负的那部分是点差）。
   如果哪天这两条挂了，说明界面上的「持有比」已经变成骗人的数字。

### 0.4.1 — 真机崩溃修复（本轮）

**这是本项目第一次拿到真机崩溃日志。** 用户直接发来了 App 自己生成的崩溃报告：

```
java.lang.IllegalArgumentException: maxHeight(-669) must be >= than minHeight(0)
    at androidx.compose.ui.unit.ConstraintsKt.Constraints(Constraints.kt:728)
    at androidx.compose.ui.text.TextPainterKt.textLayoutConstraints(TextPainter.kt:397)
    at androidx.compose.ui.text.TextPainterKt.drawText(TextPainter.kt:228)
    at com.goldlab.ui.chart.CandleChartKt...CandleChart(CandleChart.kt:229)
设备: Xiaomi 24129RT7CC · Android 16 (API 36) · arm64-v8a · GoldLab 0.4.0 (16)
崩溃点: CandleChart.kt:229 —— 价格轴刻度标签的 drawText
```

#### 根因

`drawText` 会根据 topLeft 与**当帧**画布尺寸反推布局约束：

```
maxHeight = size.height - topLeft.y
```

`topLeft.y` 一旦超过画布高度，这个值就是负的，Compose 直接抛异常。

而 `topLeft.y` 之所以会越界，是因为**绘制几何取自上一帧**：

- `canvasSize` 由 `onSizeChanged` 在**布局之后**才更新；
- Canvas 的绘制闭包却是在**组合时**创建的，捕获的是当时那个 `canvasSize`；
- 图表突然变矮时（「待作答」切到「已结算」，结算卡比提示条高 130 多 dp，
  同一帧里战绩条又多出一行提示和重置按钮，一帧之内矮了 200 多 dp），
  就会拿旧的高得多的 `chartH` 去算坐标。

对得上账：`topLeft.y ≤ chartH ≤ 旧画布高度`。要得到 `maxHeight = -669`，
旧高度必须比新高度大 669px 以上 —— 正好就是那次收缩的幅度。

#### 修法（三层）

1. **根因**：把绘图几何抽成纯函数 `ChartMath.plotGeometry(...)`，
   **尺寸只能作为参数传进来**，天然不可能用到过期值；画布太小时返回 `null`，
   调用方直接放弃这一帧。同时删掉了 Composable 层那份重复且会过期的几何计算
   （留着就是下次踩坑的陷阱）。
2. **兜底**：新增共享工具 `clampTextY`，把所有自绘文字的 Y 夹进画布内。
   CandleChart 的 6 处 + SubPane 的 1 处全部改走它。
3. **回归测试**：ChartMathTest 新增 5 条。其中一条把画布尺寸从 1×1 扫到 1200×900
   （副图 0~3 个，数万种组合），断言不变式
   **「绘图区底部 + 时间轴高度 ≤ 画布高度」**—— 这正是崩溃的充要条件。
   只要它不破，`maxHeight` 就永远是正的。

#### 顺带修正一句此前的表述

前几版报告里写的「至今没有在任何真实设备上运行过」，是**我这侧**装不上包
（`pm install` 被设备策略拦截、截屏接口不可用）造成的判断，不是实际情况 ——
用户一直在真机上运行，此前若干次界面反馈（阳线闭合后没有实体、行情不动、
挑战关不好用）都是真机观察。这次的真实崩溃日志进一步印证了这一点。已修正。

### 0.4.2 — 点差单位修复 + 存储格式调研（本轮）

用户问：「如果历史行情用 Parquet + ZSTD 会不会更好」。
为了回答得有依据，我拿内置的 33 个月真实数据做了一轮实测 —— **结果顺手揪出一个真 bug**。

#### 一、先说 bug：`Candle.spread` 的单位一直是错的

`Candle.spread` 的文档写的是「**价格为单位的**原始值，可能为 0 表示源数据未提供」，
但 `CsvCandleParser` 存的是**原始点数**：黄金 3 位小数时，CSV 里的 `200` 表示 0.200 美元，
却被原样存成了 200.0。

- 这个不一致**潜伏了很久都没被发现**，因为一直没人读它：回放、下单、成交、盈亏
  全部走 `spec.spread`（设置里那个 0.20），`Candle.spread` 只是被聚合器透传；
- 而且当时的测试**断言的正是错误值**（`assertEquals(160.0, candle.spread)`）——
  等于把 bug 锁进了回归测试里；
- 直到「猜涨跌」真的去读它：入场价被抬高 200 美元，初始权益 10000 **一局就打成负数**。

**修法（两道）**

1. 解析器按该行 OHLC 文本的小数位把「点」换算成价格（`160 点 ÷ 1000 = 0.160`）；
   取四个价格里**最多**的小数位，因为有些行会省略末尾的 0；
2. `GuessDealer` 加量级兜底：只接受 `0 < spread ≤ 价格的 1%`，超出一律退回保守默认值。

**教训**：那条断言错误值的旧测试，比没有测试更糟 —— 它给了虚假的安全感。
现在测试里明确写了两个不同小数位的用例（3 位 → 0.160，2 位 → 1.60）。

#### 二、Parquet + ZSTD 到底值不值：实测数据

**APK 体积**（折算到全部 33 个月，原始 67.85 MB）：

| 方案 | 体积 | 相对现状 |
|---|---|---|
| CSV 原始 | 67.85 MB | — |
| **CSV + deflate（现状，APK 内实测）** | **18.83 MB** | 100% |
| CSV + zstd -19 | 11.97 MB | 64% |
| CSV + brotli -9 | 15.65 MB | 83% |
| 行式二进制（原始） | 12.27 MB | 65% |
| 行式二进制 + deflate | 7.73 MB | 41% |
| 行式二进制 + zstd -19 | 7.42 MB | 39% |
| 列式二进制（原始） | 12.27 MB | 65% |
| **列式二进制 + deflate** | **6.58 MB** | **35%** |
| 列式二进制 + zstd -19 | 6.55 MB | 35% |
| 列式二进制 + brotli -9 | 6.47 MB | 34% |

**加载耗时**（单月 27,536 根，桌面 JVM 实测，取 6 次最优）：

| 路径 | 耗时 |
|---|---|
| CSV 读取 + 解析（现路径） | **161 ms** |
| 列式二进制解码（原型） | **2 ms** |

#### 三、结论

**三个数字里最反直觉的一条**：数据一旦变成二进制列式 + 增量编码，
deflate / zstd / brotli **三者的差距只有 0.5%（6.58 / 6.55 / 6.47 MB）**。

也就是说 —— **真正值钱的是「不要用 ASCII 存数字」，不是压缩算法选哪个。**

所以对这个项目的结论是：

- ✅ **换二进制列式：值。** APK 的 assets 从 18.83 MB 降到约 6.6 MB，
  APK 整体从 28.7 MB 降到约 16.5 MB；加载从 161 ms 级别降到个位数毫秒。
- ❌ **用 Parquet：不值。** 理由是 Android 上的落地成本远大于收益：
  - `parquet-mr` 依赖 Hadoop，在 Android 上跑不动；`parquet-floor` 之类也要拖 Thrift；
  - 读 Parquet 要自己实现 Thrift compact 元数据、页头、RLE/位打包、字典；
  - **ZSTD 在 Android 上没有内置实现**。本 APK 现在是纯 Kotlin（唯一的 .so 是
    10KB 的 `libandroidx.graphics.path.so`），引入 zstd-jni 要为 4 个 ABI 各带一个
    ~1MB 的 .so，**约 4MB 开销，直接吃掉三分之一的收益**；
  - Parquet 最大的价值是**与 Spark / DuckDB / Pandas 互通**，而 App 内部根本不需要这层互通。
- ✅ **压缩算法：就用 deflate。** 它在 Android 里是 JDK 自带的，零依赖零原生库，
  而实测只比 zstd 大 0.5%。

**建议做法**：自定义一个极简列式二进制（`GLB1`：varint 增量 + 每列独立存放，
约 150 行 Kotlin、零依赖、可单测），构建期把 33 个 CSV 转成它；
**同时保留 CSV 作为导入/交换格式**（用户从 MT5 导出的仍然能直接导入）。
原型已验证**无损**：同一份 2024-03，两条路径 27,536 根 K 线逐根逐字段完全一致。

> 注：加载耗时那一栏是桌面 JVM 上的相对量级；手机上绝对值会大几倍，比例大致保持。
> 原型解码器只做计时用，未作为正式格式实现。

### 0.5.0 — 内置行情改用 GLB1 列式二进制（本轮）

用户的判断：**「黄金是 3 位小数，GLB1 内部最好直接存 2350123，
而且不要把 spread 的单位问题继续埋进去。」** 两条都落进了格式定义。

#### 结果

| | 0.4.2（CSV） | 0.5.0（GLB1） |
|---|---|---|
| APK 大小 | 30,082,976 字节（28.69 MB） | **17,393,725 字节（16.59 MB）** |
| APK 内资产（压缩后） | 18.83 MB | **6.71 MB** |
| 单月加载（27,536 根） | 161 ms | **2 ms** |

**省下 12.13 MB（42%）。**

#### 格式：单位是格式的一部分，不是注释

踩过的那次事故是「`Candle.spread` 文档写价格、实际存点数」，而它之所以难发现，
是因为**单位只存在于文档里**。GLB1 把它做成显式声明：

```
偏移  长度  内容
0     4     magic "GLB1"
4     1     version
5     1     digits            ← 价格小数位；全文件唯一尺度
6     1     columnCount (=7)
7     1     reserved
8     4     barCount          uint32 LE
12    8     timeBaseMillis    int64  LE
20    8     baseCloseTicks    int64  LE  增量链起点
28    2     symbolLen         uint16 LE
30    N     symbol            UTF-8
30+N  28    7 × uint32 LE     各列字节长度
...         7 段列数据
```

| # | 列 | 单位 | 编码 |
|---|---|---|---|
| 0 | timeDeltaMs | 毫秒 | uvarint |
| 1 | openDelta | **价格 tick** | zigzag varint（相对上一根收盘） |
| 2 | highDelta | **价格 tick** | zigzag varint（相对本根开盘） |
| 3 | lowDelta | **价格 tick** | zigzag varint（相对本根开盘） |
| 4 | closeDelta | **价格 tick** | zigzag varint（相对本根开盘） |
| 5 | volume | tick 笔数 | uvarint |
| 6 | spreadDelta | **价格 tick** | zigzag varint（相对上一根点差） |

**五条硬性约定**（写在 `Glb1Format` 的 KDoc 里，并且有测试守着）：

1. 全文件**只有一个价格尺度**：文件头的 `digits`。
   `priceTicks = round(price × 10^digits)`，3 位小数时 2350.123 → 2350123。
2. **凡价格量一律用这个 tick 单位** —— 开、高、低、收、**点差**，以及它们在列里的全部增量。没有第二个尺度。
3. 唯一的非价格量是成交量，单位是 tick 笔数。
4. **全项目只有一处** tick ↔ 价格 的换算：`Glb1Format.toTicks / toPrice`。
   开高低收与点差走的是同一条代码路径，结构上不可能再错位。
5. 读取端自带自检：点差超过首根价格的 1% 就判定单位写错，归零并记警告 ——
   宁可让上层退回默认点差，也不静默按错的单位算钱。

还有一个容易被忽略的巧合，也写进了注释：**黄金是 3 位小数，而 MT5 的「点」也是 10^-3**，
所以 200 点 = 200 tick = 0.200 美元，**数值一模一样**。这正是当初那类 bug 难以察觉的原因 ——
靠肉眼比对数字发现不了，只能靠「显式声明尺度 + 单一换算点 + 自检」。

#### 源码与产物分开

- `market-data/*.csv`（33 个月，67.85 MB）—— **源头数据**，不再进 APK
- `app/src/main/assets/market/*.glb1`（33 个，11.38 MB）—— 打包资产
- 转换与校验由 `Glb1RoundTripTest` 承担：平时只**校验**，只有显式带上
  `-Dgoldlab.genMarket=1` 才写文件（Gradle 侧用 `systemProperty` 透传）。
  这样既不需要为 Android 模块手工拼一套 runtime classpath，又不会在普通测试里动源码树。
- CSV 回退路径保留：某个 `.glb1` 缺失或损坏时，只要同目录有同名 `.csv` 就照常工作。

#### 验证

- **33 个月、约 92 万根 K 线逐根逐字段比对**（时间 / 开 / 高 / 低 / 收 / **点差** / 成交量），全部一致，
  且读取过程零警告。测试 2 个用例、0 失败、0 跳过、14.2 秒。
- 另有一条"单位契约"测试：断言所有价格列都声明为 `PRICE_TICKS`，
  将来有人往格式里加价格类列却写错单位会被直接拦住。

#### 一个构建上的坑（值得记下来）

第一次打包后 APK 仍是 28.69 MB，但中央目录里的压缩数据只有 16.52 MB —— **差了 12 MB**。
逐条扫本地文件头才发现：**APK 里有 393 个本地条目，中央目录却只有 197 个**，
多出来的孤儿条目正是上一版被移除的 CSV 资产 ——
Gradle 的增量打 zip 把旧条目留在文件里了。

**结论：发布前必须 `clean` 再打包。** 增量构建出来的 APK 尺寸会虚高，
但内容是正确的（孤儿数据不会被读取）。这类问题只看"BUILD SUCCESSFUL"是发现不了的，
必须比对「文件大小」与「zip 中央目录里的压缩数据总量」。

### 0.0.2 — 移除导入/本地目录/DEMO + 修好存档（本轮）

用户的两条反馈：「有内置行情了，导入与模拟行情功能可以删了」「存档与持久化好像有问题」。
第二条查下来是**两个真 bug 叠在一起**，而且只有放在一起看才解释得通现象。

#### Bug 1：内置月份根本没有恢复路径

`initialLoad` 里判断上次来源时只看 `file:` / `uri:` 两种前缀：

```kotlin
val lastId = settings.getString(SettingsRepository.KEY_LAST_CSV, "")
if (lastId.startsWith("file:")) { … } else if (lastId.startsWith("uri:")) { … }
if (loadedSource == null) loadedSource = market.generateDemoSource()
```

而 `useBundledMonth` **从来不写** `KEY_LAST_CSV`。
所以一旦你用的是内置月份，重启后就一定落到 DEMO 数据上 —— 你上次看的那个月直接丢了。

#### Bug 2：切到内置月份时，反手就把存档抹成 0

```kotlin
replayEngine.load(src, 0)        // ← 无视存档，永远从第 0 根开始
…
persistReplay(force = true)      // ← 立刻把 0 写回数据库
```

所以「存档」实际上是**进一次废一次**：只要点过某个月份，那个月份的位置就永远是 0。
两个 bug 叠加：就算修好 Bug 1 读出存档，读到的也是被 Bug 2 抹掉的 0。

#### 修法

1. 来源键只允许由 **`SourceKeys.bundled(month)`** 一处生成（`"bundled:2024-03"`），
   `initialLoad` 与 `useBundledMonth` 都走它 —— 两边对不上这种事从此不可能再发生。
2. 启动月份选择抽成纯函数 **`StartupMonth.pick(saved, available)`**：
   优先上次玩的那个月；它已不在包里（换版本/裁数据）就退回第一个，并且是**确定性的**第一个，
   而不是随机或最后一个 —— 否则用户会以为「怎么每次打开都跳到最后一个月」。
3. `useBundledMonth` 改成**先读存档再载入**：`load(src, savedIndex)`，
   并把存档里的回放速度一并恢复。落库改成写回同一个值，幂等。

#### 回归测试（ReplayResumeTest +4）

- `bundledKeyRoundTrips` —— `bundled(m)` 与 `bundledMonth(key)` 必须能互相还原
- `bundledKeyIsNotConfusedWithOtherSources` —— DEMO / UNKNOWN / file: / uri: / null /
  `"bundled:"`（空月份）都不能被误认成内置月份
- `startupRestoresTheMonthYouWerePlaying` —— 有存档必须恢复到那个月
- `startupFallsBackWhenTheSavedMonthIsGone` —— 存档月份失效时退回第一个，且确定性

#### 移除的功能

| 移除 | 说明 |

| CSV 导入（SAF 选文件） | `importCsv` / `finishImport` / 导入进度与报告 |

### V-0.02 — 桌面图标换成用户提供的素材

#### 做法

源图 1095×1095 RGBA，是一张动漫角色面部特写，**底部有中日双语字幕**。
本机没有 PIL / ImageMagick，所以 PNG 的解码、缩放、遮罩全部手写
（`tools/make_icons.py`，只依赖标准库 zlib）。

**关键点是自适应图标的真实显示规则**：图层是 108dp，但只有**中心 72dp 保证可见**。
所以「把图铺满图层」等于「实际只看到中心 2/3」—— 我第一次就是这么做的，
结果右眼被切掉一大半。正确做法是把内容**缩进安全区**，外圈用镜像补边
（外圈只在部分启动器的视差动画里露出，直接留透明会看到锯齿）。

**字幕**：源图字幕在 y≈930 以下，裁掉底部 16% 即可。
裁完正好是「整张脸 + 一点下巴」，构图干净。

**尺寸**：内容占安全区 90%。实测 100% 会切到右眼，82% 脸太小、
且镜像外圈开始露出杂讯。90% 是「双眼完整」与「小尺寸辨识度」的平衡点。

#### 生成资源

| 资源 | 说明 |
|---|---|
| `drawable-nodpi/ic_launcher_background.png` | 432×432，照片式图标的整幅内容 |
| `drawable/ic_launcher_foreground.xml` | 有意留空（前景再放一份会与背景叠加、并在视差动画里重影） |
| `mipmap-anydpi-v26/ic_launcher.xml` / `ic_launcher_round.xml` | 自适应图标 |
| `mipmap-{mdpi..xxxhdpi}/ic_launcher.png` | 48/72/96/144/192，取自「可见区」，保证任何启动器看到的一致 |
| `mipmap-{mdpi..xxxhdpi}/ic_launcher_round.png` | 同上，套圆形遮罩 |
| 商店用 `512×512` | 放在发布目录 |

Manifest 增加 `android:roundIcon`。

#### ⚠️ 上架前的著作权风险（记在这里，不写在界面上）

这张素材是**动漫截图**，用于个人使用没有问题；但若用于**商店发布**：

- 商店审核可能要求你证明素材权利；
- 权利人可以投诉下架（国内商店尤其看重这一条）；
- 换成原创素材或明确授权素材，是唯一能彻底消除这项风险的做法。

代码与构建流程不受影响 —— 换图只需把新图路径传给 `tools/make_icons.py` 重跑一遍。

当前测试总数 **208 个用例，0 失败**。

### V-0.03 — 图标改为自绘「K 线 + FX」

用户反馈上一版（动漫截图）「图标太怪」，改用 **K 线 + FX 字样**。

这同时解决了两件事：**外观**（截图做图标确实不搭）和**著作权**（不再使用他人素材）。

#### 做法：不依赖字体

「FX」不是文字渲染出来的 —— **F 是三个矩形，X 是两条带厚度的斜杠**。
这样在任何机器上结果完全一致，不会因为缺字体出方框，也不需要打包字体文件。

输出两条路径：
- `drawable/ic_launcher_foreground.xml` —— **矢量前景**，任意尺寸都清晰，几百字节
- `mipmap-*/ic_launcher{,_round}.png` —— 传统图标兜底（48/72/96/144/192）

背景用**纯色** `@color/ic_launcher_background`（#0B0E14），不用图片：
这样任何遮罩形状下露出来的都是干净底色，不会像照片式图标那样在圆角处露出被裁的画面边缘。

#### 迭代过程（第一版被否掉）

第一版：笔画 6.5、K 线用青/红/金三色、内容占满 90% 空间。评审意见很具体：

> 字重过大、X 的交叉处糊成一坨；K 线和字母之间没有呼吸空间；
> 青红黄三色 + 金色大字导致焦点分散，小尺寸下糊成杂色；
> 视觉重心偏下，头轻脚重。

第二版针对每一条改：

| 问题 | 改法 |
|---|---|
| 字重过重、X 交叉糊成一坨 | 笔画 6.5 → 5 |
| 太挤、没有留白 | 内容从占 90% 收到约 64% |
| 三色发杂 | K 线统一单色（青），只保留「K 线青 + 字金」两个颜色 |
| 头轻脚重 | K 线整体上移、字母下移，中间留 8 单位间距 |
| 圆形遮罩切边 | 所有笔画都收进中心 66dp 安全圆内（逐点验算过） |

复核结果：「可以」。48px 桌面尺寸下 FX 依然完整可辨，圆形/圆角方形遮罩均不切笔画。

#### 两个预览

每次生成都强制走一遍预览再交付 —— 这次一共否掉了两版：
1. 照片式图标铺满 108dp 图层（实际只显示中心 2/3，眼睛被切）
2. 第一版 K 线+FX（字太重、太挤、三色发杂）

**纯看坐标是发现不了这些的，只能看渲染结果。**

当前测试总数 **208 个用例，0 失败**。

### V-0.04 — 包名/代码包名再次调整 + 纯文字图标

三项改动：

| 项 | 旧 | 新 |
|---|---|---|
| applicationId | com.cfdsimulator.app | **com.fxsimulator.app** |
| namespace（代码包名） | com.goldlab | **com.fxsimulator** |
| 图标 | 深色底 + K 线 + FX | **深色底 + 纯文字 FX** |

#### 这次真的动了 namespace

前几轮我一直建议不要动 namespace（代码包名），因为改它要动所有 package 声明与 import。
这次按要求改了 —— **74 个 Kotlin 文件，改完残留 `com.goldlab` 为 0**。

做法是纯机械变换，可以验证：

```bash
mv app/src/main/java/com/goldlab app/src/main/java/com/fxsimulator   # 目录一起搬
find app/src -name '*.kt' | xargs sed -i 's/\bcom\.goldlab\b/com.fxsimulator/g'
```

**一个正则同时覆盖三类引用**：`package` 声明、`import`、以及代码里写死的全限定名
（例如 `com.goldlab.domain.model.OrderStatus`）。

连带的自动跟随（这是之前把硬编码清干净的红利）：
- 清单里的 `.MainActivity` 是相对名 → 自动变成 `com.fxsimulator.MainActivity`
- FileProvider 授权名用的是 `${applicationId}` → 自动变成 `com.fxsimulator.app.fileprovider`

需要手动跟的一处：`proguard-rules.pro` 里的 `-keep class com.goldlab.MainActivity` → 已改。

验证结果：APK 的 dex 里 `com/goldlab` 命中 **0**，`com/cfdsimulator` 命中 **0**。

#### 图标：只留 FX

用户反馈「还不如直接用纯文字 FX」。三轮迭代：

| 版本 | 字号 | 结果 |
|---|---|---|
| 第一版 | 占满 x26..82 | 边距几乎为零，圆形遮罩下贴着切 |
| 第二版 | 0.89 | 仍被判定「留白不足、有贴边风险」 |
| **定稿** | **0.76** | 四角到中心约 25.6，遮罩圆半径 36，余量约 21% —— 「可以，直接进生产」 |

48px 桌面尺寸下 FX 依然清晰可辨（黑底金字高对比 + 粗笔画）。

#### 装之前

applicationId 又变了，所以你手机上之前装的 `com.cfdsimulator.app` 不会被覆盖 ——
**那是另一个应用**。要干净的话先卸载旧版本。
